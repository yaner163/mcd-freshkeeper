# 临期处置决策手册

券快过期时，到底该不该专门跑一趟？这份手册给判断标准。

## 决策核心：面额 ÷ 成本

**成本**包含：路程时间 + 排队时间 + 额外加购。

参考成本估值：

| 场景 | 估算成本 | 门槛 |
| --- | --- | --- |
| 顺路（本来就要去） | ¥0 | 面额 ≥ ¥5 就值得用 |
| 专程去门店 | ¥15–25（交通 + 排队 40 分钟） | 面额 ≥ ¥25 才值得 |
| 麦乐送（起送价凑单） | ¥10–15（凑单差额） | 面额 ≥ ¥30 才值得 |
| 堂食加购正餐 | ¥0 | 券能抵扣就纯赚，直接用 |

`coupon_auditor.py` 默认阈值 `LOW_VALUE_YUAN = 10.0`，低于此值会标注「不值得专门跑一趟」。这个阈值按「顺路去」设的，专程跑请按上表上调。

## 按分档给方案

### P0 今天到期

优先级最高，但**不要制造焦虑**。按面额分流：

- 面额 ≥ ¥25 → 明确建议今天用掉，给出具体门店和时段
- 面额 ¥10–25 → 建议今天内安排，附「顺路/专程」两条路径让他选
- 面额 < ¥10 → 明确说「今天不方便就算了，别为它跑一趟」，同时提示明天领新券

### P1 明天到期

- 晚上还能操作的（麦乐送）→ 提醒今晚下单截止时间
- 只能到店的 → 提醒明天营业时间，建议提前想好买什么
- 明天要上班且门店远 → 建议放弃，别为一张券打乱行程

### P2 三天内

进「本周待办」，晨间播报里带一句即可。不单独推送。

### P3 本周内 / P4 还早

不主动打扰。只在播报里统计数量。

## 组合券处理

同一时段多张券到期时，优先**凑单一次用掉多张**，而不是逐张单独跑。

策略：
1. 把同档券按适用品类分组（套餐类 / 单品类 / 代金类）
2. 代金类优先——它能抵扣任何订单，自动作用于最贵的那件
3. 单品类券绑定具体商品，用 `calculate-price` 验证叠加上限
4. 若券有互斥关系（同一订单只能用一张），明确告诉用户，别让他白试

## 临期积分处置

积分过期是纯损失，处置优先级**高于券**——券过期了只是没省钱，积分过期是资产归零。

按剩余天数：

| 剩余 | 动作 |
| --- | --- |
| ≤ 3 天 | 立即查 `mall-points-products`，推最高价值兑换方案，等用户确认后执行 |
| 4–7 天 | 播报里提示，列出可兑清单，不催 |
| > 7 天 | 只报数量，不建议动作 |

**注意**：积分兑换会实际扣减积分并锁库存，属于不可逆操作。必须走「出方案 → 用户确认 → `mall-create-order`」，不允许推断式自动兑换。

## 常见情况处理

### 接口没返回有效期

明确说「需要人工核对券面」，不要猜日期，不要归到 P4 就完事。可能是字段名变更或接口异常，应提示用户。

### 券状态是「已冻结」

冻结通常关联未完成订单。先排查是否有待支付订单占用，再决定是否催用户处理。

### 卡包券很多（> 30 张）

先给统计概览，不要一次性列全表。按分档聚合：「P0 有 3 张，P1 有 5 张」，让用户决定先处理哪档。

### 重复体检无变化

若与上次结果一致，直接说「和上次一样，没有新增临期」，不要重新贴整张表。

## 红线

- 不用脚本代签到、不做任何绕过官方接口的操作
- 不承诺「帮你保住积分」这类做不到的事
- 券和活动的真实信息以官方渠道为准，不用缓存数据回答「今天有什么活动」除非已确认是本月且未变
